## 1. The rules

Permissions may be granted at **folder**, **project**, or **song** level and inherit downward
(`docs/DESIGN.md` §3). Four rules decide every question:

1. **Most specific wins.** The grant nearest the target decides — including when it grants
   _less_. Narrowing one song to viewer under a folder-wide editor grant is a thing owners do,
   and "highest role wins" would ignore them.
2. **A deny overrides what is less specific than itself.** A deny on the song beats an allow
   on the folder. An allow on the song beats a deny on the folder. Read the direction
   carefully; both are tested.
3. **Capabilities resolve independently of role.** `canDownload` and `canInvite` each walk the
   chain separately. A viewer permitted to download and an editor refused it are both legal.
   A grant that is silent about a capability does not revoke it.
4. **Deny by default.** No grant and no membership is no access. A resource class nobody has
   wired up is unreachable rather than accidentally public (ADR 0006).

Roles, in order: `viewer` → `commenter` → `editor` → `owner`.

Scope depths swept by the matrix: `ancestorFolder`, `folder`, `project`, `song`.

Subject kinds: `member`, `sync_token`, `share_link`, `anonymous`. Only a **member**
inherits the workspace baseline — a share-link bearer or a sync token holding one would turn
every shared song into an invitation (`docs/THREAT_MODEL.md` T5).

### Why each case exists

- **folder access reaches the song inside it** — Grants inherit downward — docs/DESIGN.md §3.
- **a distant ancestor still grants** — Inheritance is not limited to the immediate parent.
- **the nearer grant wins, even granting less** — Most specific wins, including when it grants less. Narrowing one song is a thing owners do.
- **a deny on the song beats an allow on the folder** — An explicit deny overrides an allow inherited from less specific scope.
- **a grant on the song beats a deny on the folder** — A deny overrides what is _less_ specific than itself, never what is more. Read the rule carefully.
- **a deny overrides workspace membership** — Membership is the least specific statement there is.
- **membership is the baseline when nothing else speaks** — Members can reach their own workspace without a grant per song.
- **a viewer may be permitted to download** — Capabilities are independent of role — docs/DESIGN.md §3.
- **an editor may be refused download** — The same independence, in the other direction.
- **a nearer role grant leaves an inherited capability alone** — A grant silent about a capability does not revoke it. This is why the column is nullable.
- **a share-link bearer gets no membership baseline** — A link to one song must never become a key to the workspace — docs/THREAT_MODEL.md T5.
- **a sync token gets no membership baseline either** — A token is authorized against what it was issued for, never against a workspace.
- **a sync token honours an explicit grant** — Explicit grants are how a non-member subject gets anything at all.
- **nobody gets nothing** — Deny by default. An unwired resource class is unreachable, not public — ADR 0006.
- **a stranger gets nothing** — Being signed in is not access.

## 3. The full sweep

Beyond the cases above, the suite enumerates every combination of role × scope depth × deny
level × subject kind (4 × 4 × 5 × 4 = 320 cases), plus all
16 combinations of the two capabilities against every role, and the membership baseline
against every subject kind.

Expectations for the sweep come from a **one-line rule stated independently of the resolver** —
_a deny wins if and only if it sits at or above the winning grant's level_ — because a test
that derives its expected answer from the algorithm under test proves only that the algorithm
is deterministic.

## 4. Cross-workspace access

Every tenant-owned resource class carries a cross-workspace test asserting that a request
naming another tenant's id is answered **404-shaped**: the public code, the HTTP status, and
the message are all identical to a genuine not-found. A 403 would confirm the resource exists,
which is the disclosure `docs/THREAT_MODEL.md` T1 is about.

The suite reads the live database and fails if a tenant-owned table is not in this list, so a
new resource class cannot ship without its case.

A class marked **own guarded read path** is deliberately unreachable through `scopedQuery` at
all. That is stronger, not weaker: `audit_events` is read only through `queryAuditEvents`,
which requires workspace ownership, so an unguarded read of it is not one call away.
